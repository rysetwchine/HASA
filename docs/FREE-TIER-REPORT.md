# Free-tier deployment: what is done, what is not

Branch `arena/63937444-hasa` (PR #8). `main` and `production-redesign` were **not**
touched, and **nothing was deployed**. The live site is still the Stage-1 prototype.

Stack: **Vercel Free** (client) + **Render Free** (API) + **Turso Cloud Free** (database).
Render Free has no persistent disk, so Turso — not a file on the host — is the
authoritative store.

---

## Done

### 1. Audit of `server/`
Every database touch point was read and converted: `db/database.js`, `db/schema.js`,
`config.js`, `app.js`, `index.js`, `services/{auth,content,progress,ai}Service.js`,
`middleware/{auth,security,errors}.js`, `routes/{auth,student,teacher}.js`,
`db/seedContent.js`, `test/api.test.js`. Findings that shaped the design:

- the whole codebase used `DatabaseSync` synchronously, so *every* call site had to become
  `await`-able — not a driver swap;
- three `forEach(async …)` loops (seed content, teacher question create, teacher question
  update) never awaited their inserts, i.e. real silent no-write bugs on any driver;
- the schema used `PRAGMA journal_mode=WAL` and a persistent `foreign_keys` toggle, both
  unsupported on Turso;
- the XP guard relied on `INSERT OR IGNORE` + a unique index, which libSQL does support.

### 2. Turso support
- `@libsql/client@^0.18.0` (current, official), server-only, never in the client bundle.
- One async API over two drivers in `server/src/db/database.js`:
  `LocalDriver` (`node:sqlite`, WAL, prepared cache) and `TursoDriver` (`libsql://`).
  Chosen automatically from `TURSO_DATABASE_URL`, overridable with `DATABASE_DRIVER`.
- Schema moved to `server/src/db/schema.js`, PRAGMA-free, with a pre-split statement list
  for the remote driver.
- Atomicity preserved: `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` locally,
  `client.transaction("write")` on Turso. Quiz submission + attempt answers + XP ledger +
  badges commit together. Duplicate XP is still blocked by the unique index
  `idx_points_once` + `INSERT OR IGNORE`, so retries and double-clicks cannot double-award.
- Sessions stay server-side (`sessions` table), so they survive a restart or a Render
  spin-down.
- Local SQLite remains the default for dev and tests.

### 3. Safe migration — `server/scripts/migrate-to-turso.mjs`
Backs up the source file to `server/backups/hasa-<timestamp>.sqlite` (git-ignored), creates
any missing tables, copies all rows with `INSERT OR REPLACE` and original ids inside one
`PRAGMA defer_foreign_keys = ON` transaction (idempotent — safe to re-run), then verifies
**every table count and three relationship checks** and exits non-zero on any mismatch.
Flags: `--dry-run`, `--verify-only`, `--backup-dir=`, `--skip-backup`. It never writes to
the source database and never deletes Turso rows → rollback is “point the API back at the
file” (unset `TURSO_DATABASE_URL`, or `DATABASE_DRIVER=local` + `DATABASE_PATH`).
No seed or reset runs in production; `seed:reset` stays a local-only script.

### 4. Render Free config — `render.yaml`
Root directory `server`, `npm ci` / `npm start`, health check `/api/health`, free plan,
`NODE_VERSION` 22, Singapore region, `SESSION_SECRET` generated by the blueprint,
`TRUST_PROXY=1`, and `sync: false` for every secret (`TURSO_DATABASE_URL`,
`TURSO_AUTH_TOKEN`, `CLIENT_ORIGIN`, `TEACHER_SIGNUP_CODE`, AI keys). Boot fails with a
readable message instead of starting half-configured — verified:

```
TURSO_DATABASE_URL is required in production (Render's filesystem is ephemeral)…
TURSO_AUTH_TOKEN is required when TURSO_DATABASE_URL is set.
SESSION_SECRET must be at least 32 characters.
```

CORS echoes only `CLIENT_ORIGIN` with credentials; the session cookie is
`HttpOnly; Secure; SameSite=None` in production. `docs/VERCEL-API-PROXY.md` covers the
optional same-origin `/api` rewrite for browsers that block third-party cookies.

## Not done — needs your accounts

1. **Create the Turso database** (`turso db create hasa`, then `turso db tokens create
   hasa`). No Turso credentials exist in this sandbox, so no `libsql://` connection was
   ever made.
2. **Run the real migration** against your production data
   (`npm run migrate:dry-run`, then `npm run migrate:to-turso`) — the script is proven on
   a seeded copy, not on your live file.
3. **Create the Render service** from `render.yaml` and set the secrets. No Render account
   here, so spin-down behaviour and the ~30–60 s cold start are untested in practice.
4. **Set Vercel env vars** (`VITE_API_URL` → the Render URL, `VITE_SITE_URL`) and rebuild.
5. **Switch the Vercel production branch** to `production-redesign`, or merge PR #8 into
   `main`. Both were explicitly left for your approval; the live site still runs `main`.
6. **Browser/device check of the deployed pair** — no headless browser is available in
   this sandbox, so cookie behaviour across Vercel→Render in a real browser is unverified.

Recommended order: Turso → migrate (dry-run first) → Render → point Vercel at the API →
register a throwaway student and complete one lesson → restart the Render service → log in
again and confirm the XP is still there and did not double.
